# موقع maktaba.tv: كيف يُبنى وكيف يُنشر

‏maktaba.tv هو الموقع الذي تجد فيه الأسر «مكتبة» (الملحمة 60): الصفحة الأولى، وأدلة التثبيت، ثم
صفحات التنزيل والمساعدة والمشكلات والصفحات القانونية لاحقًا، وكلها بالعربية والإنجليزية. يقع في
`web/packages/website` ‏([الملف التعريفي](https://github.com/Hamza-Labs-Core/Maktaba/tree/main/web/packages/website))،
ويُبنى ويُنشر كما تُبنى هذه البوابة: عامل Cloudflare أمام ملفات ثابتة.

## البناء

يكتب الأمر `npm run build` في `web/packages/website` المجلد `dist/` بهذا الترتيب:

1. بناء التثبيت (`pnpm -C web build:install`، أدلة الملحمة 59)، منسوخًا إلى جذر الموقع في
   `/install/` و`/ar/install/`، وملفاته ذات البصمة تحت `/install/assets/`، دون أي إطار «لقطة
   الشاشة قادمة» لم تُلتقط صورته بعد (وتُبقيها المعاينة الخاصة بحزمة التثبيت)؛
2. العائلات المولَّدة (صفحات المشكلات والمساعدة والتنزيل)، كلما أضافتها قصصها؛
3. الصفحات المكتوبة يدويًا (`src/pages/`: الصفحة الأولى، وصفحة اختيار الدليل `/install/`، وصفحة
   404) والصفحات القانونية، كل منها داخل هيكل الصفحة (`scripts/shell.mjs`)؛
4. الملفات المنسوخة: أيقونات التطبيق (`favicon.ico` و`apple-touch-icon.png` والأيقونات بمقاس 192
   و512 والأيقونة القابلة للقص، والملف `manifest.webmanifest`)، ومخطط السجلات في
   `/schema/log-line.json` (معرّفه `$id`)، والملف `security.txt` بسطر `Canonical` لكل نطاق؛
5. ما تحمله كل صفحة: وسوم الترويسة (`scripts/head.mjs`: الرابط المعتمد، وبدائل `hreflang` للعربية
   والإنجليزية والافتراضية، ووسوم Open Graph، وبطاقة تويتر، والأيقونات) تُضاف حيث تخلو منها ترويسة
   دليل التثبيت نفسه؛ وبطاقة مشاركة لكل صفحة ولغة (`scripts/cards.mjs`، صورة PNG بمقاس 1200×630
   وأقل من 200 كيلوبايت)؛ والملف `sitemap.xml` ببدائل كل صفحة، والملف `robots.txt` الذي يسمّيه؛
6. الفحوص: لكل صفحة توأمها باللغة الأخرى، وتجتاز كل صفحة عربية فحص نسبة الحروف اللاتينية الذي
   تستعمله هذه البوابة؛
7. قائمة فحص الروابط (`scripts/links.mjs --write-manifest dist`): أودِعوا `dist-manifest.json` حين
   تتغيّر الصفحات، لأن التكامل المستمر يفشل إن خالف البناء.

## الصفحات القانونية

تُكتب الصفحات `/legal/privacy/` و`/legal/terms/` و`/legal/copyright/` (ونظائرها تحت `/ar/`) في
الملفات `copy/legal/<page>.<lang>.md`، كل لغة على حدة، ويبنيها `scripts/legal.mjs`؛ وترسم دالة
واحدة (`renderLegal`) تخطيطها، فيغيّرها التصميم دون أن يمسّ النصوص. وتُبنى صفحة الخصوصية من
مصادرها: قسم السحابة فيها هو `privacy.CurrentPolicy()`، تقرؤه عبر `go run ./cmd/privacy-json` في
`cloud/` (ولذلك يحتاج البناء إلى Go)، ومقابل كل قيمة بالعربية في `copy/legal/policy.ar.json`؛ وقسم
التطبيقات مكتوب من `docs/app-privacy.md`، ويسجّل نصّ كل لغة بصمة sha256 لذلك القسم
(`apps-source:`). وأي تغيير في السياسة أو في ذلك القسم دون تحديث نصّ الصفحة يُفشل البناء، مسمّيًا
القسم. وتسمّي صفحة الشروط الرخصة الواردة في `LICENSE`.

ولا يظهر نموذج الإشعار في صفحة حقوق النشر (`src/copyright-form.ts`) إلا إذا وجد البناء المتغيّرين
`WEBSITE_NOTICE_ENDPOINT` (نقطة `POST https://api.maktaba.tv/v1/moderation/notices` من الملحمة 50)
و`WEBSITE_TURNSTILE_SITEKEY` معًا. ولن يُضبط أيّ منهما قبل أن تعمل تلك النقطة، فتعرض الصفحة حتى ذلك
الحين البريد الإلكتروني للوكيل المعيّن وما يجب أن يتضمّنه الإشعار، دون نموذج. ولا تسمح بخدمة
Turnstile وبالواجهة البرمجية إلا سياسة أمان المحتوى الخاصة بتلك الصفحة.

## العامل

يحوّل `src/worker.ts` كلًّا من `www.maktaba.tv` وطلبات http العادية إلى `https://maktaba.tv`،
ويحوّل `/docs` إلى الصفحة الأولى (وإلى `/help/` حين توجد صفحات المساعدة)، ويجيب عن أي مسار غير
موجود بصفحة 404 بلغة المسار وبالحالة 404، ويضع الترويسات على كل إجابة: سياسة أمان محتوى صارمة،
وHSTS دون `includeSubDomains` (حتى لا ترثها أسماء المُرحِّل)، وسياسة التخزين المؤقت.

## طلبات الدمج

تعمل مهام `website` في `ci.yml` ‏(`_website.yml`) على كل طلب دمج يغيّر الموقع أو مصدرًا يُبنى منه:

- **website:** البناء، واختبارات الوحدات (العامل، والبناء، ووسوم الترويسة والبطاقات وخريطة الموقع،
  والسكربتات)، وفحص أوراق الأنماط، ومطابقة `dist-manifest.json` المودَع للبناء، وفحص الروابط على
  هذا البناء (كل رابط إلى maktaba.tv في المستودع، وكل `href` و`src` و`#fragment` في كل صفحة مبنية،
  ورابط كل صفحة إلى توأمها)، وفحص سريع للموقع المبني عبر العامل تحت `wrangler dev`. والموقع المبني هو
  الأثر `website-site`، وسجلّ العامل هو `website-worker-log`.
- **quality:** متصفح Playwright على كل صفحة باللغتين كما يقدّمها العامل: أداة axe بقواعد WCAG 2.0
  و2.1 و2.2 بمستويي A وAA، في الوضعين الداكن والفاتح؛ ولوحة المفاتيح (رابط التخطي أولًا، والتنقل
  بالمفتاح Tab بترتيب القراءة، وقائمة الهاتف حين يعلنها هيكل الصفحة)؛ وإطار تركيز بسماكة 2 بكسل
  وتباين 3:1 لا يغطيه شيء؛ وأهداف بمقاس 24 بكسل؛ ولا تمرير أفقيًا عند 320 بكسل؛ وتباعد النص؛
  وتقليل الحركة؛ واللغات؛ وثبات التخطيط؛ وانعكاس الاتجاه من اليمين إلى اليسار؛ والصور المرجعية.
  ويُحفظ: `website-playwright` (التقرير)، و`website-axe` (نتائج axe)، و`website-visual-diff` (عند
  الاختلاف: الصورة المتوقعة والفعلية والفرق)، و`website-worker-log-quality`.
- **lighthouse:** أداة Lighthouse على الهاتف، ثلاث مرات لكل صفحة ويُحكم على الوسيط: 95 أو أكثر في
  الأداء وإمكانية الوصول وأفضل الممارسات وتحسين الظهور، وثبات تخطيط تام (0)، و500 كيلوبايت أو أقل
  للصفحات المكتوبة يدويًا. تقيس الصفحات المكتوبة يدويًا وممثّلي كل عائلة (`e2e/representatives.json`)
  باللغتين، والعائلة كلها مرة لكل صفحة حين يغيّر طلب الدمج ما تُولَّد منه. ويجب أن تفشل فيها أولًا
  صفحة اختبار بصورة غير محدّدة الأبعاد (الضابط الإيجابي). ويُحفظ `website-lighthouse` بتقارير HTML
  وJSON، مع جدول الدرجات في ملخّص التشغيل.

## تشغيل الفحوص محليًا

في `web/packages/website`، بعد `npm ci` و`npm run build`:

```sh
npm test                 # the unit tests and the scripts' tests
npm run lint:css         # logical properties only: margin-inline-start, never margin-left
node scripts/links.mjs --dist dist   # the link check against this build
npm run e2e              # Playwright: starts wrangler dev on :8788 (its log: test-results/worker.log)
npm run lighthouse -- run --set pr --base http://127.0.0.1:8788 --out lighthouse-out/pr
```

يتخطّى `npm run e2e` الصور المرجعية على جهاز Mac: فهي لا تُرسَم إلا في الصورة التي يعمل فيها التكامل
المستمر. ويشغّل `npx playwright test e2e/a11y.spec.ts` ملف اختبار واحدًا، ويوجّه `WEBSITE_BASE`
الاختبارات إلى `wrangler dev` يعمل مسبقًا.

## تحديث الصور المرجعية

تقع الصور المرجعية في `e2e/__screenshots__/` بالاسم `<page>-<width>-<lang>[-light].png`: كل صفحة
بعرض 360 و768 و1280 بكسل باللغتين في الوضع الداكن، وكل صفحة مكتوبة يدويًا في الوضع الفاتح بعرض
1280. وحين يُقصد تغيير مظهر صفحة:

1. شغّلوا `npm run build` ثم `npm run e2e:update` (أو `pnpm -C web/packages/website e2e:update` من
   جذر المستودع). يحتاج إلى Docker: يرسم الصور في
   `mcr.microsoft.com/playwright:v<the pinned Playwright>-noble` على `linux/amd64`، أي الصورة التي
   يعمل فيها التكامل المستمر، ولا يعيد كتابة إلا ما تغيّرت بكسلاته. ولا تأتي صورة مرجعية من جهاز Mac
   أبدًا.
2. افتحوا كل صورة تغيّرت، باللغتين.
3. أودِعوها، واذكروا كلًّا منها في قسم `Reference images:` من وصف طلب الدمج مع سطر يشرح السبب. ويفشل
   فحص `Reference images` مسمّيًا الملفات حتى تُذكر كلها. وتبقى كل صورة أقل من ميغابايت واحد بلا
   بيانات وصفية.

## المسح الليلي

يعمل `website-nightly.yml` كل ليلة على `main` (ويدويًا): أداة Lighthouse على كل صفحة باللغتين، مرة
لكل صفحة، في ثماني حصص مدة كل منها 15 دقيقة. والصفحة التي تقصر عن المعيار تُقاس ثلاث مرات أخرى ويُحكم
على وسيطها. ويجعل الفشلُ التشغيلَ أحمر ويسمّي الصفحات في ملخّصه وفي الأثر `website-nightly-failures`.
ويعيد النشر التالي قياس تلك الصفحات في بنائه ولا يمضي إلا إذا نجحت، فيفكّ الحظرَ إصلاحٌ يُدمج أو
تراجعٌ عن التغيير. أما المسح الأحمر الذي لا تُقرأ قائمة صفحاته فيحظر النشر حتى ينجح مسح.

## النشر

يعمل `website-deploy.yml` عند كل دفع إلى `main` يغيّر الموقع، ويدويًا، ومرة كل شهر. يبني الموقع
ويفحصه كما يفعل طلب الدمج (مع الصفحات التي فشلت في آخر مسح ليلي)، ويرفض النشر ما دام ذلك المسح
أحمر لا تُقرأ نتيجته، ثم يمضي في هذه الخطوات (`tools/cloudflare/website-deploy.mjs`):

1. فحص الرمز (`token-check.mjs --pieces workers,dns`)؛
2. تسجيل النسخة التي تعمل الآن (`wrangler deployments status`): إليها يعود التراجع؛
3. رفع النسخة الجديدة دون تشغيلها بعد (`wrangler versions upload`)، وفحص رابط معاينتها؛
4. ترقيتها إلى 100% (`wrangler versions deploy`)، ثم تطبيق النطاقات المخصّصة
   (`wrangler triggers deploy`): ‏`maktaba.tv` و`www.maktaba.tv`، ولا اسم غيرهما؛
5. فحص الموقع الحي؛ فإن فشل الفحص عاد إلى النسخة المسجّلة وفشل التشغيل.

في النشر الأول يُنشأ العامل دون أي مسار قبل الخطوة 3، لأن رفع نسخة إلى عامل غير موجود غير ممكن.
وإن فشل فحصه الحي فُصلت النطاقات المخصّصة من جديد.

## الإطلاق

لا يُطلَق النشر إلا إذا وُجدت الثلاثة كلها: السر `CLOUDFLARE_API_TOKEN_WEBSITE` (رمز الموقع الخاص
به، مع صلاحية تعديل DNS على `maktaba.tv`، لأن النطاقات المخصّصة تكتب سجلاتها)، والسر
`CLOUDFLARE_ACCOUNT_ID`، ومتغيّر المستودع `WEBSITE_LIVE` بالقيمة `true`. وإن غاب أي منها كتبت
المهمة تنبيهًا يسمّي الناقص ونجحت. ولا يُقرأ الرمز المشترك `CLOUDFLARE_API_TOKEN` الذي ينشر هذه
البوابة أبدًا، فلا يُطلَق maktaba.tv مصادفةً. وصلاحيات الرمز مذكورة في `deploy/cloudflare/README.md`.

## التراجع

من Actions اختاروا **Deploy maktaba.tv** ثم Run workflow مع `rollback: true`. اتركوا `version`
فارغًا للعودة إلى النشر السابق للحالي، أو اكتبوا معرّف نسخة من ملخّص تشغيل نشر سابق. ويعمل الفحص
الحي بعد التراجع، ويفشل التشغيل إن لم ينجح.
