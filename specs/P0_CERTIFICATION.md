## Story 22.1 — Continuous integration pipeline

### AC1 — Six gates run in parallel

**PASS.** [.github/workflows/ci.yml](.github/workflows/ci.yml) wires up `lint`, `unit`, `integration`, `e2e`, `perf-ci`, and `build-artifacts` as separate reusable workflows under `.github/workflows/_*.yml`. All six are listed in the `ci-success` rollup's `needs:` (lines 126–134). The `lint` workflow runs golangci-lint per Go module, gofmt+vet via `make lint-go`, ruff+mypy via `make lint-py`, eslint+tsc+prettier via `make lint-web`, and migration-lint.

### AC2 — Force-merge requires recorded override

**PASS.** [.github/workflows/_pr-body-check.yml](.github/workflows/_pr-body-check.yml) fails the gate if a PR has the `force-merge` label without a `force-merge: <reason>` line ≥ 10 chars. CONTRIBUTING.md §"Pull request gates" documents the contract.

### AC3 — Three OS/arch combos for build gate

**PASS.** [.github/workflows/_build-artifacts.yml:23-25](.github/workflows/_build-artifacts.yml:23) matrix has `linux/amd64`, `linux/arm64`, `darwin/arm64`. Test gates run on `ubuntu-22.04` per `_unit.yml`, `_integration.yml`, etc.

### AC4 — Wall-clock ≤ 20 min for green PR

**NOT VERIFIABLE LOCALLY.** Tier budgets in the Makefile are 30s unit/pkg, 2m integration, 5m e2e, 2m perf-ci. Each reusable workflow has its own `timeout-minutes` cap (lint 10, unit 15, build 15). On paper these fit inside 20 min; actual runner times need a real CI run.

### Edge cases

- EC2 (fork PR): `e2e` and `perf-ci` are gated `if: …pull_request.head.repo.fork == false` (`ci.yml:69-77`), and `fork-rerun-comment` posts a maintainer-rerun message.
- EC3 (docs-only): `changes` job uses `dorny/paths-filter` with the `docs_only` filter; heavy gates skip when only `specs/`, `docs/`, or `*.md` change.

### Caveat

`pr-body-check` is a separate `needs:` entry alongside the six gates, so the pipeline is technically eight job nodes. That matches the story intent — the *user-facing* gates are six.

## Story 21.1 — Structured logging

### AC1 — slog (Go) + structlog (Python)

**PASS.** [shared/log/go/logger.go](shared/log/go/logger.go) implements `Init` returning a `*slog.Logger` with JSON in prod / text in dev, configured via `Options`. [pipeline/src/maktaba_pipeline/log/__init__.py](pipeline/src/maktaba_pipeline/log/__init__.py) provides the matching structlog config with the same field contract. TS browser logger is not present — story spec defers it ("a thin `logger`") and no Story-11 web work has landed yet.

### AC2 — Required base fields

**PASS.** Go logger uses `slog.HandlerOptions.ReplaceAttr` to rename `time` → `ts` (RFC 3339 UTC), `msg` stays `msg`, and `service`/`version`/`env` are bound via `.With(...)`. Python uses `structlog.contextvars.bind_contextvars(service=..., version=..., env=...)`. Context-binding helpers exist for `request_id`, `session_id`, `job_id`, `video_id`, `user_id`.

### AC3 — Levels with runtime control

**PASS.** Go side has `levelVar = new(slog.LevelVar)` plus `SetLevel`/`Level`; `installSIGUSR1()` is called from `Init` (see `sigusr1_unix.go`). Python `set_level()` rebinds the structlog filtering wrapper. Hot-reload via signal exists for Go; Python admin-endpoint hot-reload is the responsibility of consuming services.

### AC4 — No string concatenation of user data into msg

**PASS via lint.** The forbidigo rule in [api/.golangci.yml](api/.golangci.yml) (mirror in streaming + shared/log/go) bans `fmt.Print*` / `print` / `println`, forcing all output through slog where attributes are explicit fields. The Python side uses `select = [..., "T20"]` in [pipeline/pyproject.toml](pipeline/pyproject.toml) banning bare `print()` / `pprint()` (T201/T203).

### Redaction list

[shared/log/go/redact.go](shared/log/go/redact.go) and the matching `DEFAULT_REDACTED_FIELDS` tuple in the Python module list ~20 sensitive keys (password, token, api_key, authorization, cookie, …) and mask values via the slog ReplaceAttr / structlog processor pipeline.

### Caveat

`make lint` is currently RED because [pipeline/src/maktaba_pipeline/__main__.py:27,36,39](pipeline/src/maktaba_pipeline/__main__.py:27) contains three `print()` calls in production code. The print-ban lint *rule* works correctly — it caught the violations. But the codebase is dirty against its own contract: the implementation needs to be migrated to use `get_logger()` (or these calls need to move to a `scripts/` per-file-ignore path, or be wrapped in something T20-exempt). This makes the Story 21.1 implementation conditional: the lint exists, but the code it lints fails it.

## Story 21.4 — Health and readiness probes

### AC1 — `/healthz` always 200, never blocks on deps

**PASS.** [shared/health/go/healthz.go](shared/health/go/healthz.go) `Live.ServeHTTP` writes 200 unconditionally with `{"status":"ok","service":<name>}` — no dependency calls.

### AC2 — `/readyz` 200 only when DB + peers + warm

**PASS.** [shared/health/go/readyz.go](shared/health/go/readyz.go) runs every registered `Check` in parallel under an 800 ms cumulative budget, returns 503 with a per-check breakdown when any fail or during the warm-up window. [api/main.go:198-237](api/main.go:198) wires `DBPing` against `$DATABASE_URL` and `TCPDial` against each `MAKTABA_GRPC_PEERS` pair. Per-mode skipping when `DATABASE_URL` is unset (EC3).

### AC3 — `/api/system/health` aggregator

**PASS.** [api/internal/system/aggregator.go](api/internal/system/aggregator.go) probes every configured service's `/readyz` in parallel under a 1 s timeout, derives `ok` / `degraded` / `down` per `deriveStatus`. The endpoint is registered on the public mux at [api/main.go:137](api/main.go:137). The `Health` envelope reserves placeholders for `disk_free_bytes`, `queue_depth`, `transcribe_budget_usd_left` (deferred to Stories 21.7 / 19.7 per the source comment).

### AC4 — Probes on separate admin port

**PASS.** [api/main.go:117-125](api/main.go:117) splits `MAKTABA_HTTP_ADDR` (default :8080) and `MAKTABA_ADMIN_ADDR` (default :9100). The admin mux is built via `health.AdminMux("api", checks, warm)`. Compose's healthcheck baked into the image points at `127.0.0.1:9100/healthz` via the bundled `tools/healthcheck` binary (since distroless lacks curl).

### Edge cases

- TC3 (cold-start warming): `warmingUntil` field on `Ready` returns 503 with `reason=warming` for the first 30 s; bypassed in tests via `MAKTABA_HEALTH_WARM=0`.
- TC2 (degraded aggregator): `aggregator.go:155-159` maps `warming` → `degraded` so the UI sees one consistent shape.
