# Story 54.02 — The plugin host: Wasmtime, the WIT world and limits

> Epic 54 · Phase 1 · Depends on: 54.01 · Needed by: 54.03, 54.05, 54.06, 54.09, 54.12

## Why

Plugin code has to run somewhere that is not the pipeline worker, not the API and not the
supervisor, so a bad plugin can neither crash nor read them. This story builds that place: one
small Rust process, `maktaba-plugind`, that runs each plugin job as a WebAssembly component in
a fresh Wasmtime store with no network, no filesystem and hard limits, and that speaks to the
outside only through the `maktaba:plugin` imports it implements.

## Description

### 1. The process

- New binary `maktaba-plugind` (Rust, workspace `plugind/`), built for the four platforms by
  the same jobs that build `maktaba-server` and shipped in every payload next to it (≈ 15 MB).
- Started by the supervisor as role `plugins` (one instance per home, pattern `plugins/`),
  through Epic 51's `Supervisor.Allow(role, instance, on)`
  (`cmd/maktaba-server/internal/supervisor/components.go`). Its catalog entry is a new
  `[[component]]` in `shared/components/catalog.toml`: id `plugins.host`, `kind =
  "process+loop"` (the loop is 54.17's `api:plugins_catalog`), `group = "plugins"`,
  `placement = "home"`, `bundles = ["full", "core"]`, `on_demand = true` (54.37 §4): the
  process runs only while at least one plugin component is enabled and passes its gates.
- Listens on one unix socket, `<data>/run/plugind.sock` (mode 0600, owner the server user;
  Windows: AF_UNIX in a folder ACL'd to the server user and the AppContainer SID), for the
  pipeline's dispatch calls. It opens one outbound unix socket to the plugin API
  (`<data>/run/plugin-api.sock`, 54.04). It opens no other socket.
- `/healthz` and `/readyz` are answered on the dispatch socket (Epic 53 asks every component
  for them); the supervisor probes them through the socket.

### 2. The dispatch protocol

Length-prefixed protobuf frames over the socket (the repo already uses protobuf for the
pipeline's gRPC; a frame protocol avoids an HTTP/2 stack in the host):

| Message | Fields |
|---|---|
| `Run` | `invocation_id`, `plugin_id`, `version`, `package_path` (under `<data>/plugins/`), `export`, `job` (id, stage, subject kind/id, payload JSON, attempt, checkpoint bytes), `settings` JSON, `grants`, `token` (opaque, 54.04), `limits` (memory, timeout, fuel, scratch) |
| `Progress` | `invocation_id`, `pct`, `checkpoint` |
| `Result` | `invocation_id`, `outcome` (`ok`, `trap`, `timeout`, `memory`, `refused`), `output_hash`, `summary`, `requests[]`, `log_dropped`, `fuel_used`, `peak_memory`, `wall_ms`, `error_code` |
| `Cancel` | `invocation_id` (drain, 54.07) |
| `Preload` / `Unload` | `plugin_id`, `version` (compile and cache on install; drop on remove) |

The host never reads the database and never decides *whether* a job runs; it only runs what it
is given, within the limits it is given, and checks those limits against the manifest's maxima
(a dispatcher cannot raise them).

### 3. The WIT world

`shared/plugins/wit/maktaba-plugin.wit` defines package `maktaba:plugin@1.0.0`:

```wit
package maktaba:plugin@1.0.0;

world plugin {
  import job;        // subject, payload, settings, grants, progress, checkpoint
  import log;
  import data;
  import library;    // gated: library.read
  import transcript; // gated: transcript.read
  import media;      // gated: media.read / media.frames / media.audio
  import write;      // gated per function
  import suggest;
  import queue;
  import notify;
  import exports;
  export run: func(stage: string) -> result<run-output, run-error>;
}
```

(The stage-specific exports named by `stage.export` in the manifest are generated by the SDK
as dispatchers onto `run`; the host calls `run(stage)`. This keeps one export across languages
where some toolchains handle many exports poorly.)

Every import is implemented in the host as a thin forwarder: it checks argument sizes, attaches
the job's token and sends the call to the plugin API (54.04), which makes every decision.
Interfaces whose capability was not granted are still linked (so a plugin can be written to
degrade), but every call answers `error(capability)` without leaving the host; the API checks
again regardless.

### 4. What WASI is linked

Only: `wasi:clocks/{monotonic-clock,wall-clock}`, `wasi:random/{random,insecure,insecure-seed}`,
`wasi:io/{streams,error,poll}`, `wasi:cli/{stdout,stderr,environment,exit}` with an empty
environment and no arguments. **Not linked:** `wasi:sockets/*`, `wasi:http/*`,
`wasi:filesystem/*`, `wasi:cli/stdin`, `wasi:cli/terminal-*`. The linker is built once at start
with `Linker::allow_shadowing(false)` and no `add_to_linker_*` call for the forbidden packages;
a unit test lists the linker's names and compares them with an allow-list.

### 5. Limits

- **Engine config:** `consume_fuel(true)`, `epoch_interruption(true)`, pooling allocator sized
  from `resources.concurrency` totals, copy-on-write memory images, `cranelift_opt_level(Speed)`,
  no WASI threads, no shared memory, `wasm_backtrace_details(Enable)` for logs.
- **Per job:** a new `Store` with `StoreLimitsBuilder` (`memory_size`, `instances(1)`,
  `tables(10)`, `memories(1)`), fuel from `limits.fuel` (default: 2×10⁹ per 60 s of timeout),
  and an epoch deadline of `timeout_s` at a 100 ms tick from one ticker thread. A deadline
  trap ends the job with `timeout` within one tick plus unwind (N7: ≤ 200 ms).
- **Scratch:** when `scratch_mb > 0`, a host-side in-memory byte store reachable only through
  `job.scratch-*` calls (not a filesystem preopen), capped and dropped at job end.
- **Concurrency:** a semaphore per plugin (`resources.concurrency`) and one for the host (the
  `plugins` pool size, 54.06).

### 6. Compile and cache

On `Preload`, the host validates `plugin.wasm` is a component, runs the **import audit**
(imports ⊆ the linked set; every `maktaba:plugin` interface imported is covered by a declared
capability, else `plugin_undeclared_import`), compiles it with `Engine::precompile_component`
to `<data>/plugins/cache/<sha256>-<wasmtime version>.cwasm`, and builds an `InstancePre`. A
cache file is loaded only if its name matches the component's sha256 and the running Wasmtime
version; anything else is recompiled. Cache files are written atomically.

## Acceptance criteria

- **Given** a component that imports `wasi:sockets/tcp`,
  **when** it is preloaded,
  **then** it is refused with `plugin_forbidden_import`, and with the audit bypassed in a test
  build, instantiation fails with an unknown-import error.
- **Given** a job whose plugin loops forever with `timeout_s = 5`,
  **when** it runs,
  **then** the result is `timeout` between 5.0 and 5.2 s, and the next job on the host starts
  normally.
- **Given** a plugin that grows memory past 256 MB,
  **when** it runs,
  **then** the result is `memory`, and the host's RSS is back within 50 MB of its baseline.
- **Given** a plugin compiled and cached,
  **when** 1,000 jobs run,
  **then** instantiation p95 ≤ 5 ms and dispatch-to-first-instruction p95 ≤ 20 ms (N1).
- **Given** a dispatcher sending `limits.memory = 4 GB` for a plugin whose manifest says 256 MB,
  **when** it runs,
  **then** the host uses 256 MB and logs `limits_clamped`.
- **Given** the host's own Wasmtime version changes after an update,
  **when** a cached plugin is loaded,
  **then** it is recompiled once, not loaded from the stale cache.

## Edge cases

- **A component that does a lot of work in its start function**: start runs under the same
  fuel and deadline as the job.
- **Huge `summary` or log payloads**: the host truncates to 64 KB and sets `log_dropped`.
- **Two versions of one plugin loaded at once** (update in progress, 54.07): both
  `InstancePre`s exist; jobs carry the version they were claimed for.
- **Wasmtime security advisory**: bump the pinned version in `plugind/Cargo.toml`; caches
  recompile on next load (T08).

Shipped in the payload but not started until a plugin is enabled (on demand, 54.37 §4). The

The binary is unused without enabled plugins; a release rollback removes it.
